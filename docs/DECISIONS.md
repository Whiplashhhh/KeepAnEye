# Décisions

Une ligne par décision : décision — raison.

- Versions : TypeScript 5.9, Vite 7, Vitest 5, ESLint 9, Tailwind 4, React 19, Fastify 5 (@fastify/static 10, sans vulnérabilité connue), Playwright 1.64 — versions stables éprouvées ; Playwright aligné sur le Chromium préinstallé.
- `packages/shared` est consommé en source TypeScript ; le serveur est bundlé par esbuild — pas d'étape de build intermédiaire ni de références de projets à maintenir.
- Argon2id via `@node-rs/argon2` (binaires précompilés sur npm) — aucune compilation native requise en production.
- TOTP implémenté avec `node:crypto` (RFC 6238, SHA-1, 30 s, 6 chiffres) — quelques lignes auditables, pas de dépendance.
- L'identifiant de session n'est stocké qu'haché (SHA-256) en base — une fuite de la base ne permet pas de voler une session.
- Étape intermédiaire « mot de passe validé » portée par un cookie `kae_pre` de 5 min — le TOTP n'est jamais demandé sans mot de passe correct, et l'état reste côté serveur.
- Délai constant de 800 ms sur toutes les réponses de connexion — masque la différence entre utilisateur inexistant, mauvais mot de passe et blocage.
- Blocage progressif par IP : 5 échecs → 1 min, puis doublement jusqu'à 1 h ; blocage global après 30 échecs en 15 min — freine le brute force sans m'enfermer longtemps.
- L'IP client est lue dans `X-Forwarded-For` uniquement si la connexion vient du loopback (cas de `tailscale serve`).
- Type et projet d'une session stockés comme options utilisateur tmux (`@kae_kind`, `@kae_project`) — l'info survit au redémarrage de l'appli et reste attachée à la session.
- `window-size latest` sur les sessions créées par l'appli — le téléphone ne rétrécit pas la session vue sur le PC.
- `tmux new-session` reçoit la commande en tableau d'arguments (forme argv de tmux ≥ 3.0) — aucune interprétation par un shell.
- Modèles de session dans `config/templates.json` (surchargé par `TEMPLATES_FILE`) avec jetons `{session}`, `{project}`, `{claudeBoxDir}`, `{flags}` substitués après validation.
- Statut `Stop` → *Terminé* et la notification `idle_prompt` qui suit ne le transforme pas en *T'attend* — sinon chaque fin de tâche deviendrait une attente 60 s plus tard.
- L'appli fait elle-même la rotation de `claude.jsonl` au-delà de 5 Mo (renommage en `.1`) et détecte troncature / changement d'inode — les hooks ouvrent le fichier en ajout à chaque événement, le renommage est donc sûr.
- Lignes d'événements limitées à 64 Kio, champs texte tronqués, validation zod — données de claude-box non fiables.
- Les chemins de transcript reçus sont traduits `/home/claude` → `CLAUDE_HOME_DIR` puis vérifiés par `realpath` sous `…/.claude/projects` — pas de traversée de chemin.
- Routage frontend avec `wouter` (2 Ko) — routeur minimal suffisant.
- Service worker écrit à la main plutôt que `vite-plugin-pwa` — il ne fait que précharger l'app shell et gérer les push, tout reste lisible.
- Activité = fil des changements de statut Claude ; le journal d'audit est une sous-page de Réglages — 3 entrées de navigation maximum.
- Le hook Claude ne garde que les champs utiles (commande, chemin, motif…) tronqués, au lieu de `. + {…}` — les lignes restent petites et le contenu des fichiers écrits par Claude ne fuit pas dans les événements.
- Le hook vide toujours son entrée standard et sort en 0 — il ne peut ni bloquer Claude ni provoquer d'erreur de tube.
- Hooks installés via un petit script `~/.claude/keep-an-eye-hook.sh` référencé dans `settings.json` — installation idempotente, désinstallation propre, sauvegarde du fichier avant modification.
- `StopFailure` est reconnu s'il arrive mais n'est pas installé par défaut — hook récent, absent des versions plus anciennes de Claude Code.
- Unité systemd en `KillMode=process`, sans `NoNewPrivileges` — un serveur tmux démarré par l'appli survit aux redémarrages et `sudo` reste utilisable dans les terminaux.
- `Ctrl K` ouvre la palette sauf dans le terminal (où c'est « effacer jusqu'à la fin de ligne ») ; `Ctrl Shift K` l'ouvre partout.
- Copier / coller dans le terminal : `Ctrl Shift C` / `Ctrl Shift V` (Ctrl C reste l'interruption), plus un bouton « Coller » dans la barre de touches mobile.
- Le terminal attend une vraie mise en page avant de s'attacher et n'envoie jamais de taille < 5 lignes — sinon tmux réduirait la fenêtre et pousserait l'écran dans l'historique.
- Pour une session Claude, « dernière activité » = dernier événement de hook — l'interface de Claude redessine sans cesse, l'activité tmux ne veut rien dire.
- L'aperçu retire cadres, invites vides et indications d'interface — sinon les dernières lignes d'une session Claude ne sont que la bordure de sa zone de saisie.
- Les specs e2e qui ne testent pas la connexion utilisent une session préfabriquée par le serveur de test — un code TOTP ne sert qu'une fois, enchaîner les connexions imposerait d'attendre 30 s à chaque test.
- Captures d'écran sur un vrai tmux (socket dédié) avec des contenus et des événements de démonstration réalistes, `KAE_HOST_LABEL=homelab` — ce qu'on voit est ce que l'appli affiche réellement.
- Les fichiers statiques sont indexés au démarrage (`@fastify/static`, `wildcard: false`) — une route par fichier, le reste part vers l'app ; il faut redémarrer après un build (documenté).
- Hôte affiché via `KAE_HOST_LABEL` (défaut : hostname) — le hostname d'un conteneur ou d'une VM n'est pas toujours parlant.
- Docker : le conteneur n'embarque qu'un client tmux relié au socket de l'hôte — les sessions (shells, Claude) tournent sur l'hôte et survivent au conteneur ; un terminal « dans le conteneur » serait inutile.
- Docker : `network_mode: host` + écoute sur 127.0.0.1 — même garantie « loopback uniquement » que sans Docker, `tailscale serve` inchangé, et la vérification au démarrage reste valable.
- Docker : `KAE_TMUX_REQUIRE_SERVER=true` + `tmux-server.service` (`exit-empty off`) sur l'hôte — le conteneur ne démarre jamais de serveur tmux lui-même, sinon les sessions vivraient (et mourraient) dans le conteneur.
- Docker : montages du socket tmux et de `~/claude-box` en `create_host_path: false` — un dossier créé par Docker appartiendrait à root et casserait tmux ; mieux vaut refuser de démarrer avec un message clair.
- Docker : `~/claude-box` monté au même chemin que sur l'hôte et `HOME` = dossier de l'hôte — les chemins passés à tmux (qui tourne sur l'hôte) sont identiques des deux côtés.
- Docker : CLI Docker et plugin compose copiés depuis l'image officielle `docker:27-cli` (binaires statiques) — plus récents que les paquets Debian ; le socket Docker monté ne sert qu'à `docker compose ps` (la commande Claude est lancée par le tmux de l'hôte).
- Docker : `TZ` de l'hôte écrit dans `.env` — la plage « ne pas déranger » suit l'heure locale, pas UTC.
